## Real fixes made (committed to rebuild-2026)

1. **Subnet adaptation** — repo placeholders were `192.168.5.x`; real network is
   libvirt `192.168.122.0/24`. Updated node IP (.134), VIP (.200), NFS placeholder,
   node2 server URL.
2. **Traefik chart 40.2.0 schema** — `ports.web.redirections` rejected; the key
   moved under `ports.web.http.redirections`. (HelmRelease was failing schema validation.)
3. **Heavy HelmReleases timing out** — Longhorn/MetalLB/csi-driver-nfs exceed
   Helm's default 5m install-wait on a 2-core node; with `remediation.retries: 0`
   Flux stalled in `InstallFailed` even though pods were healthy. Added
   `timeout` + `install/upgrade.remediation.retries: 3`.
4. **paperless** — two bugs: (a) HTTPRoute `backendRef` was `paperless` but the
   bjw-s app-template names the Service `paperless-app` (`ResolvedRefs=False`);
   (b) liveness probe tripped during the slow first boot → crashloop. Added a
   `startup` probe (40×10s) + HelmRelease timeout/remediation.

## Key takeaways

- node1 is a libvirt guest on `192.168.122.0/24` behind `nuc2:10023`, not bare
  metal on a real LAN — the repo's `192.168.5.x` assumptions all needed remapping.
- On a slow/2-core node, Flux HelmReleases need `timeout` + `remediation.retries`
  or they stall in a failed install state while the pods are actually fine.
- bjw-s app-template Service name is `<release>-<serviceKey>` — HTTPRoute
  backendRefs must match (`paperless-app`, not `paperless`).
- A timed-out Helm *upgrade* with no prior good release can't roll back
  (`MissingRollbackTarget`) — `flux reconcile helmrelease --force` clears it once
  the underlying resources are healthy.
- sudo on node1 needs a password over SSH; `flux bootstrap` ran from the Mac
  through the API tunnel using `gh auth token` for `GITHUB_TOKEN`.
